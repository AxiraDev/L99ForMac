# AULA L99: сведения о совместимости

## Степени подтверждения

- **Устройство:** получено чтением HID-дескрипторов подключённой USB-клавиатуры.
- **Сериализатор:** установлено анализом машинного кода; RGB дополнительно выполнен в изолированном эмуляторе.
- **Гипотеза / ещё не испытано:** не подтверждено успешным обменом и наблюдением результата на клавиатуре.

Photo Frame проверен реальной записью и наблюдением пользователем. Для остальных функций уровень проверки указан отдельно; тесты сериализации не заменяют испытания с железом.

## USB-интерфейсы

Проводной режим: VID `0C45`, PID `800A`, product `AULA L99`, manufacturer `SONiX`.

| Usage page / usage | Input | Output | Feature | Назначение |
|---|---:|---:|---:|---|
| `0001:0006` | 8 | 1 | 0 | Обычная клавиатура |
| `000C:0001` | 16 | 1 | 1 | Составной интерфейс клавиатуры, мыши и мультимедиа |
| `FF13:0001` | 64 | 64 | 64 | Команды настройки |
| `FF68:0061` | 64 | 4096 | 0 | Legacy-канал; для Photo Frame проверенной L99 не подходит |

Длины — свойства IOHID macOS, в байтах. У интерфейса настройки нет Report ID. Windows передаёт 65-байтовый буфер с начальным нулём; macOS получает отдельно `reportID=0` и 64 байта полезной нагрузки. Начальный `04` в большинстве команд **не является** Report ID.

В конфигурации Windows-программы также указан радиоприёмник VID `05AC`, PID `024F`, Windows interface `MI_03`. Он не исследован на железе. Совпадение только VID не допускается: `05AC` используется и устройствами Apple.

## Feature-транспорт

Windows использует HID feature reports. При записи буфер из 64 байт помещается после нулевого Report ID. Для некоторых команд читается feature-ответ; подтверждением считается значение `01` в байте полезной нагрузки с индексом 3.

Пауза обычных команд в конфигурации — 35 мс. Многопакетные таблицы передаются последовательными 64-байтовыми блоками. Разные операции имеют разные требования к подтверждениям; их нельзя заменять единым правилом.

Реализация macOS открывает только `FF13:0001`, без захвата обычного клавиатурного интерфейса. При отсутствии подтверждения она прекращает последовательность. Восстановление после частично принятой транзакции пока не реализовано.

Нативные API описаны в [документации Apple](https://developer.apple.com/documentation/iokit/1588656-iohiddevicesetreport); порядок обработки нулевого Report ID дополнительно сверялся с [macOS-реализацией HIDAPI](https://github.com/libusb/hidapi/blob/master/mac/hid.c). Код HIDAPI в проект не копировался.

## Обычная RGB-подсветка

Последовательность полезных нагрузок, все по 64 байта; остальные позиции заполнены нулями:

1. `04 18` — подтверждение требуется.
2. `04 13`, байт 8 = `01` — подтверждение требуется.
3. Данные эффекта — без чтения подтверждения.
4. `04 02` — подтверждение требуется.
5. `04 F0` — в RGB-ветке подтверждение не читается.

Третий пакет:

| Индекс байта | Значение |
|---|---|
| 0 | Идентификатор эффекта |
| 1, 2, 3 | R, G, B |
| 8 | Разноцветность: 0 / 1 |
| 9 | Яркость, до 5 |
| 10 | Скорость, до 5 |
| 11 | Направление |
| 14, 15 | `AA 55` |

При эффекте 0 сериализатор обнуляет все параметры, сохраняя `AA 55`. RGB-сериализатор в оригинальном PE: метод начинается с виртуального адреса `0x433840`; проверенный участок начинается с `0x43389f`. Адреса относятся только к указанной сборке и не являются кодом, необходимым приложению.

Три эталона получены из эмуляции оригинального сериализатора с подменённым транспортом. Автоматические тесты сравнивают все 320 байт каждой последовательности с реализацией Rust. Названия и полный диапазон эффектов ещё требуют сверки; UI пока показывает числовые идентификаторы. Значение по умолчанию в конфигурации — 11.

## Переназначения

Статически восстановлена таблица 576 байт (9 пакетов). На физическую позицию приходится 4 байта, смещение — `key_index * 4`. Аппаратные индексы разрежены; в схеме этой клавиатуры представлены 84 позиции, максимальный индекс — 121. Число в названии L99 не используется как длина таблицы.

Применённые кодировки:

- Стандартное назначение: `00 00 00 00`.
- Отключить: `05 03 00 00`.
- Клавиша с модификаторами: `02 modifiers usage 00`.
- Только модификатор HID `E0`…`E7`: `02 bitmask 00 00`.
- Consumer / мультимедиа: `03 usageLow usageHigh 00`.

В байтах таблицы 574 и 575 стоит `AA 55`.

Перед таблицей: `04 18`, затем `04 11` для основного слоя или `04 27` для Fn-слоя; байт 8 второго пакета равен 9. После таблицы: `04 02`, `04 F0`. В этой ветке оба завершающих пакета запрашивают подтверждение.

Передаётся **весь выбранный слой**. Существующие назначения предварительно читаются с устройства, неизвестные записи сохраняются по снимку. Нулевая запись возвращает стандартную функцию. Для Fn используется отдельная таблица; запись не должна затрагивать основной слой. Физическая проверка consumer-кодов вне ранее подтверждённых экранных кнопок ещё требуется.

## Общие настройки

Статически восстановлена последовательность `04 18`, `04 17` (байты 2 и 8 = 1), блок данных, `04 02`. У блока данных:

| Индекс | Параметр |
|---|---|
| 1 | Константа 1 |
| 2 | Блокировка Win |
| 3 | Блокировка Alt+F4 |
| 4 | Блокировка Alt+Tab |
| 5 | Режим переключения Fn |
| 6 | Значение настройки сна |
| 8 | Значение настройки отклика |
| 62, 63 | `AA 55` |

Данные не запрашивают подтверждение; служебные пакеты запрашивают. Отображение индексов сна и отклика в UI требует дополнительной проверки по обмену Windows. Пока эти настройки экспериментальные.

## Макросы

Начало: `04 19`, затем `04 15` с числом блоков в байте 8. Далее таблица блоками по 64 байта без командного ACK, завершение `04 02`. Полная отдельная операция применения завершается также `04 F0`; без неё проверенная L99 после этой записи отказывала в новом чтении `04 18`. При назначении макроса через клавишу эта команда находится в конце последующего потока таблицы слоя.

Индекс занимает 400 байт: до 100 записей по 4 байта; младшие два байта — смещение тела макроса. Пустая существующая запись — `FF FF FF FF`. Тело начинается с 8 байт; первые два — число четырёхбайтовых действий, остальные нули. Клавиша: `00 00 usage B0` (нажать), `00 00 usage 30` (отпустить). Мышь: последний байт `90`/`10`, кнопки 1/2/4. После события задержка `delayLow delayHigh 00 50`, минимум 10 мс. Конец буфера дополнен до целого блока плюс ещё один блок; последние байты `AA 55`. Исходный сериализатор допускает буфер до 3584 байт. В этой реализации запись ограничена проверенной читаемой областью 3072 байта. Полезный размер — 400 байт индекса, по 8 байт заголовка каждого занятого слота, по 8 байт на событие с задержкой, округление до блока 64 и ещё один завершающий блок. Один макрос в пустой памяти вмещает 325 событий; при нескольких макросах и сохранённых неизвестных телах предел ниже.

Назначение макроса в таблице клавиш: `06 slot playback repeat`. Поддержаны однократный запуск и указанное число повторов. Счётчик принадлежит назначению клавиши, а не телу макроса. Неизменённые четыре байта назначения сохраняются точно; явно заданные новые счётчики формируют playback 0 при одном запуске и 1 при нескольких. Остальные способы воспроизведения пока не редактируются. Простой макрос из нажатия и отпускания A, назначенный на F12 основного слоя, проверен на реальной L99: пользователь подтвердил ввод A/Ф. В 0.7.0 пользователь подтвердил три буквы за одно нажатие F12 при счётчике 3. В 0.8.0 пользователь подтвердил запуск через Fn+F12 макроса Shift+A, отпускание Shift, пауза 500 мс, B. Мышь и остальные модификаторы отдельно не проверены.

## Индивидуальные цвета

Сначала обычная RGB-последовательность с режимом `80`. Затем `04 18`, `04 23` с числом блоков 9, таблица 576 байт, `04 02`, `04 F0`. Запись цвета расположена по `light_index*4`: `index R G B`. В конце таблицы `AA 55`. Аппаратный результат ещё не проверен.

## Реальный канал дисплея L99

Главная программа экспортирует картинку/GIF и вызывает отдельные преобразователь и последовательный загрузчик. Экран определяется как USB CDC `EEEF:268A`, 115200, 8N1, без управления потоком. На macOS используется соответствующий `IOCalloutDevice`, найденный по USB-предку, а не произвольный первый порт.

Области пользовательских изображений:

| Назначение | Начальный адрес |
|---|---|
| Фон рабочего стола | `04180000` |
| Photo Frame | `041E0000` |
| GIF | `04240000` |

Между статичными изображениями шаг `60000` hex. Загрузчик не предоставляет команд для записи по произвольному адресу или обновления прошивки.

Статичная картинка: 11-байтовый заголовок и RGB565 little-endian, строки сверху вниз. Поля заголовка: длина пикселей u32 LE, ширина u16 LE, высота u16 LE, тип 0, CRC16 пикселей u16 LE. Для 320×480 размер всего файла — 307211 байт.

GIF: таблица `20*frameCount` байт, затем кадры в контейнерах **LT**. В каждой записи: смещение кадра u32 LE, суммарная длина всех LT-кадров u32 LE, ширина/высота u16 LE, тип 3, число кадров u24 LE, задержка u16 LE в миллисекундах, CRC16 всех LT-кадров u16 LE. Смещения учитывают переменную длину упакованных кадров.

LT-кадр: сигнатура `4C 54`, ширина/высота u16 LE, число палитр u8, ориентация 3, длина контейнера u32 LE. Далее таблицы по 516 байт: длина потока в младших 24 битах, флаг RLE в старшем байте, 256 цветов RGB565 LE. После таблиц идут индексы палитры. При RLE поток состоит из пар `runLengthMinusOne, colorIndex`; одна пара описывает до 256 пикселей. Неиспользованные цвета палитры нулевые. Новая реализация использует одну палитру на кадр; ImageIO предварительно ограничивает её 256 цветами после масштабирования.

Полный контейнер из четырёх синтетических кадров 2×2 получен запуском изолированного преобразователя с подменой Qt и файловых операций; все **2204 байта** совпали с новой реализацией Rust. Проверка включает цвета, обычные индексы, RLE, смещения, длины, задержки и CRC. Старый тест только 40 байт заголовка не выявлял отсутствие LT-упаковки; такие GIF давали чёрный экран, хотя память проходила проверку.

Исправленная анимация пальцев: четыре кадра, 589832 байта, пять успешных проверок памяти при загрузке. Пользователь подтвердил движение пальцев на экране L99.

Запрос последовательного протокола: `5A A5`, длина u24 BE, команда и параметры, CRC16 LE. Длина учитывает команду, параметры и CRC, не учитывает первые 5 байт. CRC16 — отражённый полином `A001`, начальное значение `FFFF`; охватывает команду и параметры. Адрес и числовые параметры команд — big-endian.

- `64 address data` — запись до 2048 байт.
- `66 address length` — CRC32 области; после каждых не более 128 КиБ записанных данных приложение сверяет ответ с локальным CRC32 (отражённый полином `EDB88320`, начальное значение 0, без финального XOR).

Ответ: `5A A5`, длина u8, тело, CRC16 LE. Сначала приходит подтверждение `[command, FF]`, затем результат с командой, адресом и значением. Приложение проверяет CRC ответа, команду, адрес и CRC записанной памяти. Ошибка прекращает загрузку.

Проверено Photo Frame: 307211 байт, три совпавшие CRC32; пользователь подтвердил появление акулы. Повторная загрузка кнопкой SwiftUI также прошла проверку. После записи нужно выйти из Photo Frame и открыть его снова.

## Не завершено

Радиоприёмник и обновление прошивки. Найденный в основном EXE старый формат с заголовком 256 байт и HID-блоками 4096 байт не является рабочим форматом Photo Frame на проверенной клавиатуре.

## Real-time Data и часы

USB HID FF13:0001, feature report 64 байта без Report ID. Последовательность: `04 18`, `04 28` с байтом 8 равным 1, блок данных, `04 02`. Служебные команды проверяют ACK; данные не проверяют командный ACK, поскольку байт 3 содержит год, а не статус.

| Индекс в блоке данных | Значение |
|---|---|
| 0, 1, 2 | `00 01 5A` |
| 3 | Год минус 2000 |
| 4, 5 | Месяц, день |
| 6, 7, 8 | Часы, минуты, секунды |
| 10 | День недели, воскресенье 0 |
| 13, 14 | CPU %, температура CPU °C |
| 15, 16 | GPU %, температура GPU °C |
| 17, 18, 19 | В оригинале текущая/дневная/ночная погодная температура; здесь все три = температура CPU Mac |
| 20, 21 | Код погоды, влажность; здесь оба 0 |
| 62, 63 | `AA 55` |

Остальные байты нулевые. Важно: CPU начинается с индекса **13**, перед ним два резервных байта. Независимая сериализация сверена со всеми 256 байтами оригинального выхода при фиксированных тестовых значениях; эмулятор заменяет время, метрики, UI и весь HID-ввод-вывод заглушками. Публичный fixture содержит только данные протокола.

Оригинал проверяет флаг активности страницы и обновляет показатели с периодом не менее 5 секунд. Однократная отправка до открытия страницы не дала видимого результата; три повторные отправки при открытой странице привели к появлению показателей, подтверждённому пользователем. Передача не меняет изображений и не использует flash-команды CDC.

## Music Rhythm и экранный спектр

В конфигурации L99 меню Music Rhythm включено. Оригинальная программа предлагает выбор устройства звука (включая Default Loopback Device), чувствительность/амплитуду, цветовую схему, фоновый режим и яркость. В EXE прослеживается захват WASAPI loopback и обновление музыкального эффекта на компьютере. Периодический обработчик обновляет предпросмотр цветов клавиш и отправляет музыкальные уровни через HID-команду `04 78`, затем блок с режимами и уровнями, завершение `04 02`. Это отдельная функция от Consumer HID управления воспроизведением и громкостью.

Дополнительно исследована прошивка SN32F290 из вложенного обновления версии 1.03 — только локально, без установки/перепрошивки. Обработчик музыкальных уровней обновляет RGB и, при активном соответствующем экранном режиме, формирует сообщение дисплею:

`5A A5 17 62 00 12 [18 уровней] [CRC16 LE]`.

Уровни ограничиваются диапазоном 0…99. Изолированная эмуляция обработчика ARM с 18 нулевыми уровнями и с изменяющимся тестовым набором подтвердила изменение всех ожидаемых данных; CRC также рассчитана оригинальным обработчиком в изоляции. Эмулятор не открывает USB, не захватывает звук и не обновляет устройство. В этом проекте машинный код и извлечённая прошивка не распространяются.

В версии 0.4.0 реализован захват системного звука Mac и отправка уровней через HID. На проверенной L99 каждый кадр передаётся как `04 18` → `04 78` (байт 8 = 1) → 64 байта данных → `04 02`. У служебных команд проверяются совпадение кода и статус `01` в байте 3. Сырые данные не имеют командного ACK: ответ повторяет уровни, и его байт 3 не является статусом. Повтор сырых данных не выполняется. Между операциями поток использует задержку 5 мс; последовательная очередь общая с настройками и real-time data.

| Индекс в блоке | Содержимое |
|---|---|
| 0 | Цветовая схема спектра 0…11 |
| 1 | Цветовая схема фона 0…11 |
| 2 | Яркость фона 0…100 |
| 3…20 | 18 уровней 0…99 |
| 21…63 | Нули |

Идентификаторы схем: 0 выключено, 1 зелёный/жёлтый/красный, 2 радуга, 3 обратная радуга, 4 градиент, 5 смена спектра, 6 белый, 7 красный, 8 оранжевый, 9 жёлтый, 10 зелёный, 11 голубой. Вызовы исходного сериализатора передают 25 слотов уровней; исследованная прошивка использует первые 18. Тестовый fixture хранит исходные три отчёта (выбор, данные, завершение); вход `04 18` и правила ACK проверяются отдельно.

Анализ macOS выполнен собственным кодом: Core Audio process tap → mono PCM → FFT 2048 с окном Hann → 18 логарифмических полос 60 Гц…16 кГц → сглаживание и диапазон 0…99. На USB отправляется последний актуальный кадр с частотой до 12,5 Гц. Запись изображения и применение настроек временно приостанавливают музыкальный поток. Прямые команды UART `62` из Mac не отправляются: сообщение экрану формирует сама клавиатура.

Физическое движение экранной волны и реакцию клавиш на звук подтвердил пользователь. Кнопки плеера на самой клавиатуре работают отдельными мультимедийными HID-событиями и не требуют такого захвата.


## Чтение конфигурации (0.5.0)

Проверено на подключённой L99 через feature-отчёты 64 байта, report ID 0, коллекция FF13:0001. Каждая область читается отдельной транзакцией: `04 18` → команда чтения → сырые блоки → `04 02`. Запрос содержит число блоков в байте 8.

| Область | Opcode | Блоков | Используемых байт |
|---|---|---:|---:|
| Подсветка | `12` | 1 | 64 |
| Основной слой | `10` | 9 | 576 |
| Fn-слой | `26` | 9 | 576 |
| Общие настройки | `16` | 1 | 64 |
| Индивидуальные цвета | `22` | 9 | 576 |
| Макросы | `14` | 48 | 3072 |

После заголовка чтения может прийти ACK или сразу первый блок данных. Получается **N+1 сырой блок**, где N задано в запросе. Последний блок не входит в запрошенную область, но участвует в контрольной сумме. ACK `04 02` содержит сумму всех байтов всех N+1 блоков в байтах 4…7, little endian, UInt32. Все шесть областей аппаратно прочитаны с совпавшими суммами. Footer AA55 не требуется для чтения: заводские таблицы могут его не содержать.

Читатель использует только перечисленные команды входа/чтения/завершения. Команда `04 F0` и данные конфигурации при чтении не отправляются. При несовпадении суммы снимок целиком отвергается.

Перед изменением слоя сохраняется его сырая таблица. Редактор заменяет выбранные записи и сохраняет неизвестные действия. Для макросов сохраняются номера слотов; неподдерживаемые тела сохраняются побайтово, смещения пересчитываются. Ссылки на удалённые поддерживаемые макросы очищаются до замены таблицы макросов. Новые слоты не используют ещё занятые номера из исходного снимка. Для подсветки и общих настроек сохраняются неизвестные поля и старшие биты известных флагов. Проверенная область макросов ограничивает запись 3072 байтами.

Синтетические тесты чтения и сохранности находятся в `tests/ConfigurationTests.swift`; пользовательские снимки устройства не являются публичными fixture-файлами.


## Подтверждение записи и жизненный цикл USB (0.6.0)

ACK проверяется по длине 64, совпадению команды в байтах 0–1 и статусу 1 в байте 3. Программный успех требует также нового чтения. Для слоя и индивидуальной палитры сравниваются 574 байта до завершающего маркера; для настроек — четыре младших бита блокировок/Fn, сон и отклик, без флага самой операции записи; для подсветки — применённые параметры режима и цвета. Для макросов сравниваются словари слотов и полные тела, без зависимости от расположения неиспользуемого заполнителя.

Каждая фоновая операция привязана к IORegistry ID и поколению подключения. Пробуждение увеличивает поколение даже без смены ID. Отмена проверяется перед USB-пакетами и чтением ответа. Старые завершения не меняют состояние новой операции. Сырые блоки настройки не повторяются; неудача требует чтения нового состояния с сохранением локального черновика.

Список HID-интерфейсов для отображения читается напрямую из IORegistry. HID-клиент создаётся через IOHIDDeviceCreate по конкретному registry ID только для обмена. Неизменённые распознанные тела макросов, включая допустимые нулевые задержки, сохраняются побайтово вместо нормализации новым сериализатором.
